# ADR-0016: 생성 제한 시간 540초 + 품질 경계 유지형 드래프트 축소

- **Status:** Accepted (사용자 결정, 2026-09-23)
- **Date:** 2026-09-23
- **Supersedes:** [ADR-0011](./0011-async-plan-generation.md)의 Decision 2 중 300초 제한과 그에 연결된 성능 계약
- **근거:** 백로그 068 병렬 A/B · [Firebase Functions 할당량](https://firebase.google.com/docs/functions/quotas)

## Context

운영 로그 22건 중 6건이 모두 285초 자체 마감에서 실패했고, MiniMax-M3 `adaptive` 병렬 A/B의 최장 정상 호출은 285.7초였다. 즉 300초 플랫폼 제한과 285초 자체 마감은 비정상 요청만 끊는 장치가 아니라 정상적인 꼬리 지연 결과도 경계에서 버리고 있었다.

한편 `thinking:disabled`는 p90을 182.7초에서 32.7초로 줄였지만, 새 하드 게이트 통과율이 88.9%에서 47.2%로 떨어지고 후보 밖 운동·장비 위반·파이프라인 실패가 늘었다. 속도만 얻기 위해 이를 운영 기본값으로 바꾸면 사용자가 요구한 결과 품질을 지킬 수 없다.

DraftPlan에는 최종 결과에 쓰이지 않는 출력도 있었다. `name`·`coaching_cue`·`substitution_options`는 확장 엔진이 읽지 않고, LLM의 `focus`는 코드가 근육군 기준 제목으로 다시 만들며, LLM의 유산소 제안도 결정적 유산소 엔진이 사용하지 않는다. 이 필드는 모델의 출력과 판단량만 늘린다.

## Decision

1. `plansWorker`의 플랫폼 제한 시간을 **540초**로 올린다. 워커 자체 데드라인은 기존 15초 정리 여유를 유지해 **525초**이며, 미니앱 폴링 상한도 **540초**로 맞춘다.
2. 540초는 **신뢰성 상한**이지 속도 목표가 아니다. 접수 p95 ≤ 2초는 유지하고, 정상 생성의 개선 목표는 별도로 **p90 ≤ 60초**로 둔다. 540초 안에 완료하지 못하면 잡을 `error`로 확정하고 실패 통지·사용권 환불 등 기존 복구를 그대로 수행한다.
3. 운영 추론 모드는 품질이 검증된 `adaptive`를 유지한다. `thinking:disabled`와 adaptive 공통 출력 상한은 채택하지 않는다.
4. 새 생성 요청에는 **compact DraftPlan 스키마**를 보여 준다. 최종 결과에 쓰이지 않는 `name`·`coaching_cue`·`substitution_options`·`cardio_kind`를 빼고, `focus`는 빈 문자열 상수로 제한한다. `week`에는 근력 세션만, 아이템에는 근력 운동 선택만 받으며 휴식일·유산소는 코드가 만든다. 저장된 예전 드래프트 호환성을 위해 정본 DraftPlan 검증 스키마는 바꾸지 않고, 모델 응답은 계속 그 전체 스키마와 WeeklyPlan 값 규칙을 모두 통과해야만 저장한다.
5. compact 변경의 속도 효과는 배포 뒤 기존과 같은 대표 프로필 반복 실측으로 판정한다. 품질 게이트를 통과한 결과만 성공 표본으로 세며, p90 ≤ 60초를 못 맞추면 백로그 068의 다음 후보를 비교한다.

540초는 Firebase 2세대 task queue 함수의 공식 최대 제한인 1,800초 안이다. 알려진 285초 꼬리 지연과 수리 호출에 여유를 주면서도, 외부 provider가 멈춘 작업을 무기한 유지하지 않는 값으로 선택했다.

## Consequences

- 정상 응답이 기존 285초 자체 마감에 걸려 사라지는 문제는 줄어든다. 플랫폼 강제 종료 15초 전 `error` 기록과 실패 통지를 할 수 있다는 기존 안전장치도 유지된다.
- 최악의 실패 확정 시간은 5분에서 9분으로 늘어난다. 그래서 UI는 9분을 예상 완료 시간으로 약속하지 않고, 백그라운드 생성·재진입 폴링을 유지한다.
- compact 스키마는 모델이 만들던 미사용 텍스트와 유산소 제안을 줄이지만, 추론 지연 전체를 없애지는 않는다. 실제 개선 폭은 배포 후 계측 전까지 수치로 단정하지 않는다.
- 전체 호환성 스키마와 코드 소유 확장·검증을 그대로 거치므로 INV-1과 기존 결과 수용 기준은 약해지지 않는다.

# ADR-0017: 미니앱 진행 중 기록을 Firestore에 미러링하고 복구한다

- **상태:** Accepted (2026-09-23, 사용자 요청). 앱 코드 출시·토스 실기기 확인은 별도 게이트. 결정 3에서 운동 중 편집만 같은 기기 입력을 이어 쓰던 범위는 [ADR-0018](./0018-same-device-plan-edit-progress.md)이 넓힌다.
- **대체 범위:** [D22-6](./mvp-decision-log.md#d22)의 「완료 전 체크는 기기에서만 보관」 부분. 완료 세션의 Firestore 정본과 [D19](./mvp-decision-log.md#d19)는 유지한다.

## 배경

사용자가 완료 체크와 수정한 세트가 사라진다고 보고했다(백로그 072(**사용자 지시로 삭제 2026-10-02**)). `localStorage`를 IndexedDB로만 바꿔도 웹뷰 origin 저장소 삭제·기기 변경에는 대비하지 못한다. 완료 세션은 이미 Firestore에 있지만 완료 전 입력은 기기에만 있었다. 사용자는 데이터 보존을 우선하고 Firestore 추가 비용을 수용했다.

## 결정

1. 진행 중 요일별 입력을 `weekly_plans/{uid}/weeks/{week_start_date}.progress_drafts.{day_index}`에 별도로 저장한다. 완료 세션 `sessions`와 혼동하지 않는다. 계정 인증·용량/형식 검증·`plan_id` 확인·revision 비교를 거친다. 다른 기기의 수정은 자동 병합하거나 덮지 않고 사용자 선택을 요구한다.
2. 화면은 로컬 기록을 즉시 보존하면서 서버 초안을 읽고 미러링한다. 서버 오류 때는 로컬 기록을 지우지 않고 실패 상태를 표시한다. 서버 기록을 선택할 때 로컬 사본을 보관한다. 계정 전환·손상 응답은 조용한 초기화로 처리하지 않는다.
3. 최종 `PerformedSession` 저장과 초안 닫기는 같은 주차 문서 쓰기로 처리한다. 이미 저장한 세션은 초안만 닫고 세션을 다시 쓰지 않는다. 저장 뒤 `GET`으로 완료 기록을 확인하기 전에는 로컬 기록을 지우지 않는다. 플랜 재생성·빈 주는 열린 초안을 전부, 요일 편집·이동은 영향받은 요일만 `closed_reason: plan_replaced`와 증가한 revision으로 닫는다. 영향받지 않은 요일은 열린 초안의 플랜 생성 시각을 같은 트랜잭션에서 갱신해 기존 입력을 계속 쓸 수 있게 한다. 새 입력은 플랜 생성 시각을 비교한 뒤 옛 초안을 같은 문서의 보관 맵에 옮겨야 시작할 수 있다. 운동 중 직접 편집한 요일은 새 동기화 객체로 다시 열고, 기기 입력을 보존한 채 옛 초안을 보관한 후 이어 쓴다.
4. Firestore `(default)` 데이터베이스에 PITR 7일, 일일 백업 보존 7일, 삭제 방지를 적용한다. **백업 일정이 만들어진 것과 첫 백업 파일이 존재하는 것은 다르다.** 계정 삭제·기록 초기화 요청은 기존 계약대로 처리하며 운영 백업 보존 정책을 프라이버시 고지와 맞춘다.
5. IndexedDB 단독 이전은 채택하지 않는다. 토스 네이티브 `Storage`로의 계정별 기존 로컬 기록 이전은 백로그 072 §4의 별도 출시 단계로 남긴다. 이 ADR만으로 오프라인에서 서버에 도착하지 않은 입력의 무손실을 보장하지 않는다.

## 결과

- 새 API와 필드는 생성 API 계약 §2.4.1, [데이터 모델 SavedWeeklyPlan](../architecture/02-data-model.md#savedweeklyplan-미니앱-플랜-정본--백엔드-영속-d19)에 둔다.
- 데이터베이스 추가 쓰기·읽기와 백업 비용이 발생한다. 기존 사용자 문서를 일괄 변환하거나 삭제하지 않는다.
- 로컬 브라우저·가짜 API 왕복과 격리된 실제 Firestore 임시 문서 쓰기/읽기는 구현 검증이다. 토스 실기기, 실제 계정의 기존 기록 이관, 배포 후 동작은 이 검증으로 대신하지 않는다.

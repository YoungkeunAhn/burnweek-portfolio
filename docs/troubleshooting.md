# 트러블슈팅

운영하면서 실제로 겪은 장애 5건의 원인 분석입니다. 괄호 안 커밋 해시는 비공개 운영 저장소 기준이고, 코드와 테스트는 이 저장소에서 바로 볼 수 있습니다.

## 1. 실기기 토스 로그인이 전부 401 — 검증 경로와 운영 경로가 달랐다

- **상황**: 토스 파트너 API는 mTLS로만 붙습니다. 인증서를 p12로 변환해 함수에 넣었고, 연결 확인용 probe 스크립트는 PEM으로 붙었습니다. probe는 성공하는데 실기기 로그인은 전부 401이었습니다.
- **원인**: 함수 로그에 `Unsupported PKCS12 PFX data`. p12가 `pbeWithSHA1And40BitRC2-CBC`로 암호화돼 있었고, Node 22(OpenSSL 3)는 legacy provider 없이 RC2-40을 거부합니다. 클라이언트는 정상이었고, 검증 경로(PEM)와 운영 경로(p12)가 달라서 probe가 문제를 못 잡았습니다.
- **해결**: p12를 AES로 다시 만드는 대신 변환 단계 자체를 없애고 PEM으로 통일했습니다. 이제 테스트·probe·런타임이 같은 경로로 인증서를 읽습니다.
- **결과**: 배포 후 mTLS 오류가 사라지고 실패 사유가 토스 인가 코드 검증 단계(`invalid_grant`)로 넘어간 것을 로그로 확인했습니다.
- **코드·테스트**: [`backend/src/auth/toss.ts`](../backend/src/auth/toss.ts), PEM으로 로컬 mTLS 서버를 띄우는 [`backend/test/toss-auth.test.ts`](../backend/test/toss-auth.test.ts) (07bc058b, 2026-08-25)

## 2. 파이프라인 개편 뒤 헬스장 플랜 생성이 전부 실패

- **상황**: 코드가 슬롯 골격을 만들고 LLM은 후보 중 하나만 고르는 새 방식(P1)을 헬스장 환경에 적용한 뒤 생성이 실패했습니다.
- **원인**: 접수 핸들러와 워커가 후보 목록을 각자 만들고 있었습니다. P1 결과를 워커가 옛 방식(P0)의 허용 목록으로 검사해 거부했습니다. 평가용 헬스장 프로필 11개 중 11개가 재현됐습니다.
- **해결**: 후보 준비를 [`prepareGeneration`](../backend/src/generation/prepare.ts)으로 빼서 두 곳이 같은 입력(요청·파이프라인 설정·접수 시각)으로 같은 후보를 보게 했습니다. 워커의 독립 최종 검증은 그대로 둡니다.
- **결과**: 워커를 재배포하고 회귀 테스트 17건을 추가했습니다. 수정 전 가드로 되돌리면 헬스장 기본 테스트 11건이 실패하는 것(변이 확인)까지 확인했습니다.
- **테스트**: `P1 worker regression: ...` 17건 — [`backend/test/generation-api-contract.test.ts`](../backend/test/generation-api-contract.test.ts) (c599b84f, 2026-10-23)
- **같이 내린 판단**: 같은 날 첫 조회 지연(콜드스타트 약 3초)도 봤습니다. 최소 인스턴스 1개 유지는 30일 유휴비 $17.46~22.68로 계산된 뒤 승인하지 않았습니다.

## 3. TTL이 동작하지 않아 생성 잡과 데이터가 계속 쌓였다

- **원인**: `expires_at`을 ISO 문자열로 저장했습니다. Firestore TTL은 Timestamp 필드만 인식합니다.
- **해결**: Date 타입으로 바꿨습니다. 같은 변경을 다른 모델로 3라운드 교차 리뷰하면서 삭제 쪽 문제 10건을 함께 찾았습니다.
  - 하위 경로 DELETE가 전체 삭제로 번지는 문제
  - 확인과 삭제 사이의 경합(TOCTOU)
  - 탈퇴 직후 늦게 도착한 요청이 데이터를 되살리는 문제
- **결과**: 사용자 데이터 삭제를 트랜잭션 하나로 묶고, 계정 버전을 비교해 탈퇴 후 도착한 쓰기를 거부합니다. ([`backend/src/auth/account.ts`](../backend/src/auth/account.ts), 229d9c9d)

## 4. 프로덕션에서만 조회 API가 500

- **상황**: 실기기에서 "다른 운동으로 변경"에 종목이 하나도 안 나온다는 보고.
- **원인**: 프로덕션 로그에서 `orderBy(__name__, "desc")`가 `FAILED_PRECONDITION`으로 실패해 현재 플랜·교체 후보·이력이 모두 500이었습니다. 내림차순에는 복합 색인이 필요했습니다.
- **해결**: 기본 색인을 쓰는 오름차순으로 읽은 뒤 뒤에서 자르도록 4곳을 바꿨습니다(`latestWeeks`).
- **남은 한계**: 사용자당 주차 문서를 모두 읽습니다. 주차가 늘면 색인으로 바꿀 자리라고 코드 주석에 남겼습니다. (3d403aa4, 2026-09-08)

## 5. 생성 꼬리 지연 — 추론을 끌 것인가, 시간을 늘릴 것인가

- **상황**: 초기 모델(MiniMax 추론 모델)의 운영 로그(2026.09.09~22, 22건)에서 성공 16건의 p50 136초·p90 274초, 나머지 6건(27%)은 285초 자체 마감으로 실패했습니다.
- **검토**: 추론을 끄면 골든 프로필 12종 × 3회 A/B에서 p90이 182.7초 → 32.7초로 줄지만, 하드 게이트 통과가 32/36 → 17/36으로 떨어졌습니다.
- **채택**: 추론을 유지하고 워커 제한을 540초로 늘리되, 플랫폼 종료 15초 전에 기다리기를 끝내고 잡을 `error`로 기록하며 생성 한도를 환불하도록 했습니다. 진행 중인 LLM 호출까지 취소하지는 않습니다(늦게 온 결과는 저장되지 않음, 취소 전달은 이슈 #5). 토스 푸시는 성공 때만 보내므로, 앱은 폴링으로 실패를 확인합니다. ([ADR-0016](decisions/0016-generation-timeout-and-compact-draft.md))
- **이후**: 운영 모델을 GLM-5.3-Flash로 바꿨습니다. 골든 프로필 16개 로컬 실측에서 16/16 성공, p90 42초였습니다. 품질은 계열이 다른 심판 모델 2개가 6개 프로필을 순서를 바꿔 두 번 판정(엇갈리면 무승부)해 Haiku 대비 2승 0패 4무였습니다. 하네스는 [`backend/test/eval/judge.ts`](../backend/test/eval/judge.ts). 공개한 `backend/test/results/model-ab*.json`은 심판 투표를 모은 집계 결과이고, 비교에 쓴 생성 플랜 원본은 들어 있지 않아 이 저장소만으로 다시 판정할 수는 없습니다. 추론 A/B(`reasoning-ab-2026-09-23.json`)는 실행별 측정값이 들어 있습니다.
